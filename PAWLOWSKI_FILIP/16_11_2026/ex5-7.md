# Exercise 4 – note

`LibraryCatalog` is in `library_catalog.py`. The full test suite is in `test_library_catalog.py` and contains:

- a `setUp()` that creates a catalogue with three known books (Dune, The Trial, The Castle),
- success and failure tests for every method,
- `test_borrow_then_return_restores_availability`,
- `test_failed_add_leaves_catalog_unchanged` and `test_failed_borrow_leaves_catalog_unchanged`, which compare a deep copy of the catalogue taken before the failed call with the catalogue after it.

# Exercise 5 – Organising the suite

The tests are split into four classes, each with its own `setUp()`:

| Class | What it covers |
|---|---|
| `TestAddingBooks` | adding books, duplicate ISBN, `count()` |
| `TestRemovingBooks` | removing existing and unknown books |
| `TestSearching` | `find_by_author`, `find_by_isbn`, `available_books` |
| `TestBorrowing` | `borrow`, `return_book`, failed operations |

All four `setUp()` methods call the same helper `make_catalog()`, so the three books are defined in one place.

### Running with -v

```bash
python -m unittest -v test_library_catalog
```

Part of the output:

```text
test_add_book_success (test_library_catalog.TestAddingBooks.test_add_book_success) ... ok
test_remove_unknown_book (test_library_catalog.TestRemovingBooks.test_remove_unknown_book) ... ok
test_find_by_author_ignores_case (test_library_catalog.TestSearching.test_find_by_author_ignores_case) ... ok
test_borrow_success (test_library_catalog.TestBorrowing.test_borrow_success) ... ok
```

**Observation:**

With `-v` every test is printed on its own line, and the class name is part of the line. The output is grouped by topic, so when a test fails it is clear at once which area of the catalogue is broken.

# Exercise 6 – subTest

```python
def test_is_even_for_many_inputs(self):
    cases = [
        (0, True), (2, True), (10, True), (100, True), (-4, True),
        (1, False), (7, False), (99, False), (-3, False),
    ]

    for number, expected in cases:
        with self.subTest(number=number, expected=expected):
            self.assertEqual(is_even(number), expected)
```

The test uses nine inputs.

### Deliberately breaking one input

`(100, True)` was changed to `(100, False)`. Output:

```text
FAIL: test_is_even_for_many_inputs (...) (number=100, expected=False)
...
AssertionError: True != False

Ran 1 test in 0.000s

FAILED (failures=1)
```

**Observation:**

- The output names the exact input that failed (`number=100, expected=False`).
- Only one failure is reported, which means the other eight inputs were still executed and passed. Without `subTest()`, the first failing `assertEqual` would stop the loop.

# Exercise 7 – skip and expectedFailure

### 1. Skip a test

```python
@unittest.skip("not implemented yet")
def test_export_to_csv(self):
    self.fail("This would fail, but it is never executed.")
```

### 2. Skip only on Windows

```python
@unittest.skipIf(sys.platform == "win32", "posix only")
def test_posix_only(self):
    self.assertNotEqual(sys.platform, "win32")
```

On Linux and macOS this test runs. On Windows it is skipped with the reason "posix only".

### 3. Expected failure

```python
@unittest.expectedFailure
def test_known_bug_title_search(self):
    self.assertEqual(LibraryCatalog().find_by_title("Dune"), [])
```

The method `find_by_title()` does not exist yet, so the test fails with `AttributeError`, which is what we expect.

### Reading the summary line

With `-v`:

```text
test_export_to_csv (...) ... skipped 'not implemented yet'
test_known_bug_title_search (...) ... expected failure
test_posix_only (...) ... ok
```

Summary of the whole suite (run on Linux):

```text
Ran 27 tests in 0.002s

OK (skipped=1, expected failures=1)
```

- **OK:** no test failed in an unexpected way.
- **skipped=1:** one test was not run (the `@skip` one). Skipped tests still count in "Ran 27 tests". The `skipIf` test is not skipped here because the platform is not Windows; on Windows it would show `skipped=2`.
- **expected failures=1:** one test failed as announced and this does not make the suite fail.

If a test marked `@expectedFailure` starts to pass (here, if `find_by_title` were implemented), the summary changes to:

```text
FAILED (skipped=1, unexpected successes=1)
```

This is a useful signal: the marker is outdated and should be removed.

# Conclusion

- **Exercise 5:** Splitting tests into classes makes the verbose output read like a table of contents.
- **Exercise 6:** `subTest()` reports every failing input separately and does not stop at the first one.
- **Exercise 7:** Skipped tests and expected failures are counted in the summary line, so they are never hidden.
